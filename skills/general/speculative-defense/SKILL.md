# 投机防御（Speculative Defense）

只有能说出「这个情况发生过」的防御才写，说不出就不写。

大多数防御挡的是想象出来的事，不是真发生过的事。这种代码几乎没有成本——加了不会让任何检查失败，
删了也不会，所以只增不减，越攒越多，最后把真正的失败原因盖住。

## 什么时候用

- 要写防御分支了：`try`/`catch`、输入校验、空值兜底、大小或数量上限、`timeout`、`retry`、
  防抖、并发保护、平台或版本分支
- 用户说「加固一下」「更健壮」「考虑边界情况」
- 改动突然变胖，要审一遍

## 什么时候不用

- 修一个有证据的故障：有日志、有复现、有 issue。那是 bug fix，正常改
- 只是文案、注释、格式化、版本号
- 用户明确要求「不管会不会发生都得拦住」：照做，但把这条写进非目标

## 1. 先填表，不写代码

打算加的防御，一条一行列出来。空表也交。

填好的样子：

| 防御 | 它防什么 | 证据 | 结论 | 写在哪 |
| ---- | -------- | ---- | ---- | ------ |
| 响应超过 1000 条就分页 | 前端卡顿 | 没有：接口实测最多 40 条，也没人反馈卡 | 不处理 | — |
| 请求失败重试 3 次 | 偶发连接超时 | 有：issue #12 里每天约 2 次 | 处理 | 请求封装 |

结论只有两种：处理、不处理。全是「处理」的表，多半没认真评。

## 2. 什么算证据

四种，从强到弱：

1. 亲眼见过——日志、复现步骤、具体数字
2. 上游承诺——能指出哪个文件或哪段文档保证了它不会那样发生
3. 类型挡住——编译器已经不允许
4. 有人报过——issue、用户反馈、这次对话里说过

下面这些不算：「保险起见」「生产环境什么都可能发生」「以后可能会用」「文件理论上可以很大」。它们的
共同点是从「接口允许」推出「事情会发生」。那是猜。

没有证据就是不处理。理由写在讨论里，别写进注释——注释放久了，后来的人会把它当成「这个情况真的
存在」的证据。

## 3. 讨论：最小改动，说清不做什么

表后面接两句话：改哪几个文件、改什么；这次明确不处理哪些。

这一步不写代码。

## 4. 执行：只改确认过的

确认之后再动手。改的时候冒出表里没有的防御分支（比如顺手加个 `try`/`catch`），停下来问。

别顺手重构、顺手改名，也别动确认范围之外的文件。

## 5. 写在哪

只看两件事，不看目录叫什么：

1. 这段代码收外部输入吗？文件、网络、用户输入、第三方返回、命令行参数、环境变量都算。收——防御
   写这边，一条对一个证据，尽量只写一次。
2. 只是内部变换吗？是——不写，形状由调用方保证。

所以纯库、纯函数、纯数据处理的项目，一般一条防御都不该有。输出和呈现这一侧也别写兜底，该显示
什么就显示什么：空、错、不可用。

同一个防御在几个地方各写一遍，本身就是问题。选一边，或者提到一处公共的地方。

## 6. 改完自检

- 加了几条防御分支，各对上面表里的哪一行？
- 表里写了「不处理」的，真的都没处理吗？
- 有没有哪条防御，只有类型上根本不可能的情况才会碰到？

对不上任何一行的，删掉。
